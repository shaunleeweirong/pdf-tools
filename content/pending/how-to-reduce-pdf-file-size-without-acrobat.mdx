## When compression helps, and when it doesn't

This is the part most guides get wrong, and it matters a lot.

In-browser PDF compression works by [rasterizing](https://en.wikipedia.org/wiki/Rasterisation) every page to a JPEG image. For a PDF made of scans or photos, that's fine: images are already taking up the space, and re-encoding them at a lower quality reclaims it.

For a text document (a Word export, a contract, an invoice), it's the wrong tool. Text in a PDF is normally stored as vector font data, which is very compact. When the compressor turns the page into a JPEG of that text, the file gets much larger. In our testing, a 20-page text report went from 23.5 KB to 1.4 MB after medium compression. That's not an anomaly; it's what happens to vector text every time.

**Use compression only if your PDF contains scans or photos.** To check: try to select a word with your cursor. If text highlights, you have a vector text PDF and compression will increase the file size, not reduce it. If nothing highlights, it's a scan or image-heavy file and compression is the right tool.

## What makes a PDF large in the first place?

Knowing the cause helps you pick the right fix:

- **High-resolution images or scans.** A scan at 300 [DPI](https://en.wikipedia.org/wiki/Dots_per_inch) is far larger than the same content at 150 DPI. In-browser compression addresses this directly.
- **Embedded fonts.** Programs like Word or InDesign often embed entire font files inside the PDF, adding substantial overhead even when the document uses only a fraction of the characters. This cannot be fixed by JPEG compression.
- **Revision history.** Some PDF editors save every editing step inside the file. Older files from InDesign or Illustrator can carry years of revision data. A fresh export strips this.
- **Hidden layers or elements.** Design files sometimes include hidden layers that don't appear on the page but still take up space in the file.

If your PDF is large but contains only text, embedded fonts or revision history are the likely cause. Compression will make it worse. In those cases, opening the file and printing it to PDF through your operating system's built-in PDF printer can strip the overhead without touching the content.

## Free built-in options on each platform

**Mac: Preview's Quartz filter.** Open the PDF in Preview, choose File > Export, set the format to PDF, and pick **Reduce File Size** from the Quartz Filter dropdown. This can shrink image-heavy files, but Preview applies the same compression to everything with no way to adjust the level. A dedicated compressor gives you more control, especially for files where you need to balance size and readability.

**Windows: Print to PDF.** Open the PDF in Microsoft Edge, press Ctrl+P, and choose **Microsoft Print to PDF** as the printer. This re-renders the file and can strip overhead data like revision history. The result varies by file type and rarely matches a dedicated compressor on image-heavy PDFs.

**Chrome on any platform.** The same print-to-PDF approach works in Chrome and applies across Mac, Windows, Linux, and Chromebook. It's best for stripping overhead rather than reducing image data.

None of these built-in methods match a dedicated in-browser compressor for image-heavy PDFs, but they're useful for text files bloated by overhead data.

## Don't compress the same file twice

This advice appears often online, and the numbers don't support it. We ran an already-compressed PDF back through the compressor and measured what happened:

- Second pass at the same level (Medium): **315.3 KB became 598.9 KB**, nearly double.
- Second pass at a stronger level (High): 315.3 KB became 297.8 KB, a saving of 5.6%.

Re-rendering a page that is already a JPEG, then encoding it as a JPEG again, adds compression artefacts and data rather than removing them. A second pass at a higher level claws back a tiny amount at the cost of visible quality loss. It's not worth it.

The correct approach: if one pass is not small enough, go back to the **original file** and compress it once at a stronger level.

## When compression isn't the right fix

**The file is already small enough.** Many PDFs that seem hard to share are under 1 MB to start with. Check the file size before trying anything.

**You only need a few pages, not all of them.** If a 20-page report is too large to email, the recipient probably only needs one or two pages anyway. Use the [Split PDF tool](/split-pdf) to extract just those pages, then check the size. Fewer pages mean a smaller file before compression enters the picture, and it's often the single most effective step.

**The PDF is too large for email.** [Gmail and Outlook both cap messages at 25 MB](https://support.google.com/mail/answer/6584), and Base64 encoding of the attachment adds roughly 33%, so the practical ceiling is around 18 MB. Most PDFs that won't attach aren't near that limit. The usual cause is a portal or recipient with a stricter limit, or a poorly exported file that's larger than it should be. A fresh export from the source application often fixes it cleanly.

**You need to keep the file confidential.** If privacy is a concern, choose a tool that processes files locally in your browser rather than uploading them to a third-party server. Our Compress PDF tool never sends your file anywhere.
