# pdf-tool measurements

Every number quoted in a blog post comes from this file. Nothing here is estimated, rounded up for effect, or carried over from another product's marketing. If a claim cannot be traced to a row below, it does not belong in a post.

**Measured:** 2026-07-27 (2026-07-26T23:15Z to 23:20Z)
**Environment:** macOS (darwin arm64, Apple silicon), Node v26.4.0, Chromium 149.0.7827.55 headless, Next dev server on localhost:3000.

## How to reproduce

```bash
# 1. Build the corpus. <photoDir> needs 6+ distinct JPEGs.
node scripts/generate-test-corpus.mjs .playwright-mcp/corpus <photoDir>

# 2. Node-side tools (merge, protect, unlock)
node --experimental-strip-types scripts/measure-tools.mjs .playwright-mcp/corpus

# 3. Compression, which needs a real browser (see note below)
npm run dev
node scripts/measure-compression.mjs .playwright-mcp/corpus
```

Compression rasterizes pages through a `<canvas>`, so it cannot run in Node. `measure-compression.mjs` drives the actual site in Chromium and records the exact size of the PDF blob the tool hands back, by wrapping the `Blob` constructor before the run. It is the same code path a visitor exercises.

## The corpus

Generated by `scripts/generate-test-corpus.mjs`, so results are reproducible.

| File | Contents | Size |
|---|---|---|
| `text-report.pdf` | 20 A4 pages, body text and headings only, no images | 23.5 KB |
| `photo-deck.pdf` | 6 pages, each a full-bleed 720pt raster image, every page a distinct JPEG | 913.4 KB |
| `mixed-document.pdf` | 3 A4 pages, body text plus a small raster logo per page | 35.0 KB |

The image deck uses six *different* images on purpose. Embedding one image six times gets deduplicated by pdf-lib into a single stream, which would produce a file far smaller than a real deck and make any ratio measured against it meaningless.

**Known limitation of the current corpus.** The six images are variants (rotations and crops at 1600px and 1200px) of `public/authors/chris-p.jpg`, which is an *illustrated avatar*, not a photograph. Illustration has flatter colour and harder edges than a photograph, and JPEG treats the two differently. The direction of every finding below holds regardless, because it is driven by rasterization rather than by image content, but **the exact compression percentages for the image deck would shift on a corpus of real photographs.** Posts should describe this file as an "image deck", never as photographs. Replacing the source images with real photographs and re-running is the highest-value improvement to this corpus.

## Compression

`/compress-pdf`, measured in Chromium against the running site.

| File | Level | Before | After | Change | Time |
|---|---|---|---|---|---|
| photo-deck.pdf | High (smallest) | 913.4 KB | 175.6 KB | **−80.8%** | 788 ms |
| photo-deck.pdf | Medium | 913.4 KB | 315.3 KB | **−65.5%** | 820 ms |
| photo-deck.pdf | Low (best quality) | 913.4 KB | 703.5 KB | **−23.0%** | 853 ms |
| text-report.pdf | Medium | 23.5 KB | 1400.8 KB | **+5861%** | 1938 ms |
| mixed-document.pdf | Medium | 35.0 KB | 171.2 KB | **+389%** | 510 ms |

### The finding that matters

**This compressor makes text-based PDFs dramatically larger.** A 20-page text report grew roughly 60x, from 23.5 KB to 1.4 MB. A mostly-text document with a small logo grew about 5x.

That is not a bug. The tool rasterizes every page to JPEG, which is stated on the tool page itself ("this is a light, in-browser compression that rasterizes pages. Text becomes an image"). Rasterizing helps enormously when a page is already a photograph and hurts enormously when a page is text, because text stored as vector glyphs is tiny and text stored as a photograph of glyphs is not.

Consequences for content:

- Never tell a reader to compress a text PDF to fit an email limit. It will get bigger, and they will not check.
- Compression advice must be conditional on what is *in* the PDF. Scans and photo decks: yes. Text documents, invoices, contracts, forms: no, split or zip instead.
- Text PDFs that are too large for email are usually large for a different reason (embedded fonts, an oversized logo, revision history), and the fix is different.

Timings were taken warm, after the dev server had compiled the route. Treat them as an order of magnitude, not a benchmark. Cold first-run in dev was around 5 s for the same 6-page deck.

### Compressing twice does not help

Common advice, including in two of our own posts before this was measured, is to run compression a second time on the output to squeeze out more. Feeding the Medium output back in:

| Input | Level | Before | After | Change |
|---|---|---|---|---|
| photo-deck at Medium (already compressed once) | Medium | 315.3 KB | 598.9 KB | **+90%** |
| photo-deck at Medium (already compressed once) | High | 315.3 KB | 297.8 KB | −5.6% |

A second pass at the *same* level nearly doubles the file. The already-rasterized page gets re-rendered at scale 1.5 and re-encoded, and re-encoding a JPEG that has already been through the mill adds data rather than removing it. A second pass at a *higher* level claws back 5.6%, which is not worth the quality cost.

Correct advice: pick the right level the first time. If Medium is not enough, start again from the original at High. Never chain passes.

## Merge

`/merge-pdf`, via `lib/pdf/merge.ts` (pdf-lib) in Node.

| Inputs | Sum of inputs | Output | Change | Time |
|---|---|---|---|---|
| text-report + mixed-document | 58.5 KB | 57.7 KB | −1.2% | 49 ms |
| all three files | 971.9 KB | 970.5 KB | −0.1% | 21 ms |

Merging does not inflate the result. The output came in marginally *under* the sum of its inputs both times, because shared PDF structure is written once. Useful for the common worry that combining files will push the total over an email limit: it will not, beyond the size the parts already add up to.

### Merging strips interactive form fields

Built a PDF with one text field (`applicant.name`, value "Jane"), merged it with a second document, and reloaded the result:

```
fields BEFORE merge: [ 'applicant.name' ]
pages AFTER merge  : 2
fields AFTER merge : []
```

Page count is correct and page content survives, but the document no longer has any form fields. `merge()` uses pdf-lib's `copyPages`, which copies page content rather than the document's AcroForm.

This matters most on exactly the workflow our job-application post describes, where people merge a filled-in form with a cover letter. Advice: flatten a filled form before merging, so the values are painted into the page and cannot be lost. We have a `/flatten-pdf` tool for this.

Not yet checked: whether the filled *values* remain visible as static graphics after merging, or disappear along with the fields. Until that is measured, posts should say the fields are lost and recommend flattening first, without claiming what the page looks like afterwards.

## Protect and unlock

`/protect-pdf` and `/unlock-pdf`, via `lib/pdf/qpdf.ts` (qpdf-wasm, AES-256) in Node.

| Operation | File | Before | After | Change | Time |
|---|---|---|---|---|---|
| Protect | text-report.pdf | 23.5 KB | 24.6 KB | +4.8% | 426 ms |
| Unlock | text-report.pdf | 24.6 KB | 23.6 KB | −4.3% | 106 ms |
| Protect | photo-deck.pdf | 913.4 KB | 914.4 KB | +0.1% | 171 ms |
| Unlock | photo-deck.pdf | 914.4 KB | 913.5 KB | −0.1% | 134 ms |

Encryption overhead is roughly a fixed ~1 KB, not a percentage. It reads as +4.8% on a 23.5 KB file and +0.1% on a 913 KB one. Password protection therefore has no practical effect on whether a file fits an email limit.

Unlocking returns the file to within a hundred bytes of its original size, so the round trip is effectively lossless in size terms.

**Wrong passwords were rejected** on every encrypted file, verified in the same run (`qpdf: invalid password`).

## Not yet measured

Claims in these areas are not currently backed by first-hand data, so posts should not imply testing:

- Behaviour on very large files (100 MB+)
- Mobile browsers, and Safari specifically
- Split, rotate, watermark, sign, form fill, and the remaining tools
- Visual quality loss at each compression level, as opposed to file size
- Compression ratios against genuine photographs, as opposed to the illustrated images currently in the corpus
- Whether the values in a filled form remain visible after merging, or vanish with the fields
